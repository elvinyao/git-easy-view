# Git Easy View：团队分支概览工具设计

日期：2026-09-29。状态：总体方向与技术选型已确认，本文待用户审阅。

## 1. 目标与已确认决策

为团队提供一个集中部署的网页，查看 20～100 个仓库中 master/main、release、feature 的来源、计划目标以及实际合入进度。核心展示单位是仓库和分支；成员无需逐个打开完整提交图理解全局。

已确认的需求：

- 支持 GitHub.com、GitLab.com、自建 GitLab 和 GitHub Enterprise Server，按实例配置连接。
- 管理员从平台选择仓库，服务自动拉取到服务器并维护分析副本。
- 团队共用网页，按工具内部的项目授权，不要求继承每个人的平台权限。
- 管理员维护连接、仓库、项目、成员与分支归属；普通成员查看已授权项目。
- 使用 Python + FastAPI，前端使用普通 HTML/CSS、Jinja2 和 jQuery。
- 使用 PostgreSQL、SQLAlchemy、Alembic；后台使用 RQ + Redis；Git 分析调用原生 Git；通过 Docker Compose 部署。

最初的本机目录扫描需求已收敛为集中导入远程仓库。第一版保留项目和仓库的层次列表；服务器缓存目录是内部存储，不作为需要用户管理的业务分组。成员电脑上未推送的分支、未提交修改不在当前数据范围内。

## 2. 本文补齐的建议默认值

以下是实现所需的设计建议，尚未作为用户逐项确认的要求：

| 项目 | 建议默认值 |
| --- | --- |
| 运行时 | Python 3.13，开发基础镜像为 python:3.13-bookworm |
| 登录 | 工具本地账号和密码，由管理员创建账号；预留后续接入公司统一登录的边界 |
| 同步周期 | 每 5 分钟检查到期仓库，允许管理员按仓库调整；新增仓库立即排队 |
| 并发 | 初始最多 2 个仓库同步任务并行，同一仓库串行处理 |
| 分页 | 仓库和分支各每页 50 条；展开仓库后按需加载分支 |
| 平台认证 | 管理员配置服务使用的访问令牌；Git 拉取首先支持 HTTPS |
| 首次 PR/MR 导入 | 获取全部开放记录及最近 90 天更新的已关闭记录；更早历史可以由管理员按时间范围补充导入 |

页面必须显示 PR/MR 的导入覆盖范围。未找到记录只意味着当前已获取的数据中没有记录，不能据此判定从未合并。

## 3. 第一版范围

包含：登录与项目授权、平台连接检查、仓库选择和导入、定时及手动同步、仓库和分支列表、来源与目标配置、提交关系分析、PR/MR 证据详情、同步失败提示。

后续扩展：本机或已有目录扫描、完整提交图、SSO、平台权限自动继承、Webhook、SSH 拉取、跨仓库发布编排、精细内容等价分析。

第一版不提供 push、merge、rebase、删除远程分支等远程写入功能。仓库的 clone/fetch 只更新服务自身的分析副本。项目和归属配置的编辑保存在本工具中。

## 4. 页面与交互

使用服务端模板渲染页面。jQuery 负责事件、Ajax、局部替换和同步进度查询；列表及详情的 HTML 由模板统一生成。静态资源随应用部署，不依赖公网 CDN 或 Node.js 构建流程。

| 页面 | 主要内容 |
| --- | --- |
| 项目概览 | 获授权的项目、仓库数量、同步状态；跨仓库按分支名称、角色和关系状态筛选 |
| 项目仓库列表 | 仓库名称、平台实例、主干、分支数、Git 与平台数据的最后同步时间；支持展开 |
| 分支列表 | 分支名、角色、来源候选与依据、计划目标、相对比较对象的领先/落后、提交包含状态、PR/MR 状态、最近提交时间 |
| 分支详情 | 具体比较对象与提交标识、公共祖先、独有提交、PR/MR 链接、人工配置记录及推断解释 |
| 管理界面 | 平台连接、仓库导入、项目与成员授权、角色规则、活跃 release、同步任务和失败记录 |

分支列表以主干、release 置顶，其余按最近提交时间排序。多个目标在详情中分别展示；列表显示主要比较对象与其他目标数量，不将分支强制归为一棵唯一父子树。

筛选与分页条件保存在 URL 中，刷新或分享页面地址可以恢复查询。未获得项目权限的访问不会显示项目、仓库、分支或 PR/MR 信息。

手动同步由管理员触发。查看成员可以刷新已缓存的页面数据，但不能触发平台扫描、导入或修改任务配置。

## 5. 关系模型与准确性边界

### 5.1 分支身份与角色

分支由“仓库身份 + 完整引用名”定位，分析时再记录对应的提交 OID。仓库身份使用“平台实例 + 平台仓库 ID”，不使用单独的仓库名称。PR/MR 的来源与目标分别记录仓库身份，避免将 fork 中的同名分支当成本仓库分支。

远程默认分支初始标记为主干；release/ 和 feature/ 前缀作为可编辑的角色规则。名称匹配只表示角色，不表示来源或祖先关系。管理员可以逐个覆盖角色并指定活跃 release。活跃 release 初始为空；标记后加入预计算范围，不影响其他 release 在列表中正常显示和按需比较。

### 5.2 创建来源

Git 分支没有永久的父分支字段，新拉取的副本也不包含开发者机器上的完整 reflog。工具不承诺还原真实创建过程。

优先展示管理员指定的来源，并标记为“人工指定”。没有配置时，对同仓库主干及已标记的 release 分析公共祖先，将有公共历史的分支作为来源候选，显示公共祖先及双方差异，统一标记为“推测”。不存在公共历史时显示“无法判断”。多个候选并列展示，不仅凭最近提交时间自动选择唯一父分支。

共同祖先只能说明历史关系，不能证明创建来源。第一版不使用缺乏可靠证据的百分比置信度，也不将 PR/MR 的目标直接视为创建来源。

### 5.3 计划合入目标

开放 PR/MR 的目标作为平台提供的计划目标。管理员可以补充人工目标；多个不同目标同时保留并注明来源。没有开放记录或人工配置时，计划目标为空。

比较对象与计划目标是不同字段：管理员可以指定主要比较对象；否则，在只有一个计划目标时使用该目标；其他情况默认与仓库主干比较。采用主干作比较不会生成“计划合入主干”的结论。

### 5.4 当前提交关系

对于来源分支 F 和比较分支 T，基于一次分析快照中固定的双方 OID 计算：

- 领先：F 可达而 T 不可达的提交数量。
- 落后：T 可达而 F 不可达的提交数量。
- 相同：双方 OID 相同。
- 已包含：F 的头提交是 T 的祖先；这表示 F 当前可达提交已全部被 T 的历史包含。
- 未全部包含：不满足祖先关系，但存在公共历史。
- 无共同历史：没有公共祖先。
- 未分析或分析失败：没有可用结果，与数值 0 明确区分。

使用 git merge-base、git rev-list 等原生命令计算。提交可达性不代表文件内容相同；即使头提交已被包含，目标后续的 revert 或修改仍可能改变功能。第一版使用“提交已包含”等准确措辞，不展示“功能已上线”或“代码内容一致”。

默认预计算各分支与主干、管理员标记的活跃 release、以及其同仓库计划目标的关系。其他分支比较按需计算并缓存，避免无条件计算全部分支两两组合。主要比较对象保持可见，不隐藏其余尚未分析的目标。

跨 fork 的 PR/MR 可展示平台来源和目标；第一版不自动拉取额外 fork，也不将其当成本仓库的提交比较结果。

### 5.5 平台合并记录

独立记录 PR/MR 的开放、关闭未合并、已合并状态，以及平台提供的合并时间、合并提交、来源提交和目标分支。平台未提供的字段保持未知。

“PR/MR 曾经合并”和“当前分支提交已被目标包含”必须同时存在，不能互相覆盖：

- PR 合并后 feature 新增提交：显示“PR 已合并；当前提交尚未全部包含”。
- squash、rebase、cherry-pick：可以出现平台记录已合并而原提交不可达；显示两份证据，不把不可达解释为代码肯定没进入目标。
- 缺少平台记录：只展示 Git 可判定的事实，其他情况显示“未确认”。
- 分支被删除：已获取的 PR/MR 记录保留，并提示分支当前不存在；不沿用旧提交比较结果冒充当前状态。
- 同名分支被删除后重建或被强制更新：按新 OID 重新计算；旧 PR/MR 属于历史记录，不自动认定其对应当前分支内容。

第一版不自动判定多提交 squash 或人工解决冲突后的内容等价。相关扩展可以以后增加独立的内容证据类型。

## 6. 应用结构与数据

维护一个 Python 应用代码库，按职责拆分模块；Web、后台 Worker 和周期调度进程共享业务代码，通过 Docker Compose 分别启动。

| 模块 | 职责和边界 |
| --- | --- |
| Web 与模板 | HTML 页面、局部片段、请求校验、会话与项目权限 |
| 平台连接器 | GitHub/GitLab 各自实现连接检查、仓库列表、默认分支及 PR/MR 分页同步，输出统一模型 |
| Git 仓库服务 | clone/fetch、引用快照、原生命令执行、超时和同仓库互斥 |
| 关系分析 | 消费固定 OID 和平台证据，计算事实、候选来源与展示状态 |
| 任务服务 | 调度、入队、重试、并发限制及任务恢复 |
| 持久化 | 业务数据、同步覆盖范围、快照和任务状态，提供事务边界 |

Git 副本以无工作区的 bare 仓库存储完整分支历史，不进行业务源码检出和执行。初次导入后采用增量 fetch。仓库对象保存在持久磁盘，PostgreSQL 保存元数据与分析结果。

主要数据实体：用户、项目、项目成员、平台连接、仓库、项目仓库关联、分支快照、分支配置、关系证据、PR/MR、同步任务、审计事件。

一个仓库可以加入多个项目，底层分析副本共用。分支角色和人工关系配置属于仓库级并在这些项目间共享，仅管理员可修改。来源证据至少包含证据类型、双方仓库/分支/提交身份、获取时间、记录链接或配置操作者。

平台连接器读取公司实例的可用能力和版本。接口字段缺失时降级为未知，不影响本地 Git 分析。API 分页和历史覆盖必须显式处理，不能只读取第一页后视作完整数据。

## 7. 同步与任务可靠性

1. 管理员选择仓库并关联项目，系统创建持久任务记录并入队。
2. Worker 获取仓库互斥锁，首次 clone 或执行增量 fetch。
3. 固定本次引用与 OID 快照，计算需要更新的关系。
4. 分页同步 PR/MR，保留平台数据的独立获取时间和覆盖范围。
5. 使用数据库事务发布完整的 Git 分析快照；平台数据独立发布，页面分别显示两者的新鲜度。
6. 周期调度按 next_sync_at 检查到期仓库并补充任务。

Redis 保存队列并启用持久化；PostgreSQL 保存任务请求和状态。入队失败或队列重启后，由调度进程核对未完成记录并补排。任务需可重复执行；按仓库去重和加锁，限制同实例请求并发，旧任务不得覆盖较新的快照。

Git 分析缓存按仓库、双方 OID 及分析规则版本区分。人工配置或平台记录变化时，更新对应展示结果。未变化的提交关系可复用。

网络和限流错误延迟重试；凭据失效停止该连接的自动重试并提示管理员；单仓库失败不阻断其他仓库。Git 失败保留上次成功快照；平台失败仍可更新 Git 结果。首次同步未完成时显示“正在导入”，不展示虚构的零分支或零差异。

## 8. 项目授权与部署

系统管理员可以管理全局资源。普通成员通过项目成员关系获得查看权限。授权在后端执行，覆盖列表、搜索、详情、HTML 片段、JSON、同步状态和 PR/MR 元数据；撤销成员关系后，下一次请求立即应用新权限。

本地密码以成熟密码哈希方案保存；会话使用安全 Cookie，修改操作校验 CSRF。平台令牌仅服务端解密使用，密钥通过部署配置提供，日志和网页不输出令牌。选择专用账号或令牌及平台允许的最小权限；工具仅调用读取接口与 Git 拉取操作。

平台实例和拉取地址由管理员批准；平台返回的 URL 必须校验，不允许任意地址接收其他实例的凭据。公司 CA 可通过部署配置提供，TLS 校验保持开启。Git 子进程使用参数数组、参数校验和超时，避免拼接 shell 命令；分支名及 PR/MR 内容按数据转义展示。

部署包括 Web、Worker、周期调度、PostgreSQL 和 Redis，前置公司 HTTPS 入口。数据库、Redis 和 Git 缓存采用独立持久卷。备份包含数据库和凭据加密密钥；Git 缓存可重新拉取。实际存储和并发配置通过目标仓库测量后确定，不按仓库数量单独承诺容量。

所有项目命令必须通过 bash .agent/run.sh 执行。主机仅用于源文件编辑与只读检查；Docker 不可用时报告问题，不回退到主机执行。依赖版本在实施阶段锁定，不在运行时追随 latest。

## 9. 验收与测试

| 验收场景 | 预期结果 |
| --- | --- |
| 导入多个 GitHub/GitLab 实例仓库 | 实例及仓库身份正确，分页数据完整，仓库可加入同一项目 |
| 仓库列表展开、筛选和分享 URL | 按需加载，恢复筛选，不一次渲染全部分支 |
| 普通分叉、快进、merge commit | 领先/落后与原生 Git 对照一致，包含关系正确 |
| squash/rebase/cherry-pick、后续新增提交、revert | 历史包含和平台记录独立显示，不错误宣称内容或功能已合入 |
| 多个来源候选、多目标及无共同历史 | 保留多关系，无法判定时明确说明 |
| 空仓库、删除/重建分支、force push、fork 同名分支 | 没有误关联，过期快照和历史记录可区分 |
| 未授权用户直接请求详情/片段/接口 | 不泄露仓库和平台记录；撤销授权后即时生效 |
| 平台限流、凭据失效、分页中断 | 失败范围明确，旧数据有时间标识，不误报完整成功 |
| Worker 中断、Redis 重启、重复入队 | 任务可恢复，同仓库互斥，新旧快照发布顺序正确 |

Git 算法测试使用容器内创建的真实小型 Git 历史；连接器使用固定 API 样例覆盖两种平台、缺失字段、分页与错误。浏览器测试覆盖登录、授权、导入、展开分支和查看证据。

性能验证先使用 100 个小型测试仓库，每仓库至少 50 个分支，确认任务并发上限、分页及按 OID 缓存有效；真实仓库接入后记录首次导入和增量同步耗时。测试样本不构成真实大仓库的性能承诺。

## 10. 实施顺序

1. 应用骨架、数据库迁移、本地账号和项目授权。
2. Git 原生分析与关系语义测试，使用测试仓库。
3. GitHub/GitLab 连接器、导入、队列和同步快照。
4. 项目概览、仓库/分支列表、证据详情和配置页面。
5. 异常恢复、权限回归、部署与操作文档、端到端验证。

这是交付顺序，不是已经执行的实施计划。本文经用户审阅后，再依据 Superpowers writing-plans 拆解具体任务。
